## Bug 修复（2）：粒子发射器在后面又炸一次

**现象**：`E:\谱子\adofai-CE-old\adofai-CE-old\cetx\main_old.adofai` 53/63/73/83 格 `EmitParticle`（tag 1-9/1-12/1-15/1-18，count 100）依次炸开；AES 里已经炸过的发射器在后面又炸一次。

**根因**：`ParticlePreviewDomain.ApplyEmit` 的触发条件不是"跨过事件"，而是"闩为空 + 现在在事件之后"，外加一条墙钟 1 秒重复规则。三条重复路径：① 停在事件附近，墙钟 1 秒后重炸；② 回拖时 `ResetLatches()` 清 `EmittedLast`，之后只要在事件之后就**在当前位置**补炸（最像用户看到的现象）；③ 直接跳转跨过也补炸。

原生 `ffxEmitParticlePlus.StartEffect` 只做一次 `particleSystem.Emit(count)`，`Decode` 只读 count/tag——**没有 duration，没有持续喷**。

**修法**（提交 `b084823`）：只按跨过判定 `previousTime < 起点 <= time` 且单步跨度 `<= EmitCrossingMaxStep(0.25s)`；回到事件之前清闩、停在事件之后不补、跳转不补；删除 `EmitRepeatSeconds`/`EmitActiveWindowSeconds`/`EmittedAtUnscaledTime`；新增 `[ParticleEmit]` 探针（VerboseDiagnostics 门控）。

**教训**：`ResetLatches` 清闩是为了让 `Start` 重跑，但同一批闩被 Emit 共用 → 语义污染。以后加"已应用"闩要问一句：这个闩清掉之后，那个动作会不会在错误的位置重放。

**验证**：0 错误 / 49 警告；SHA256 `C56F48C…`；`DONE gameRunning=True`（23:13:39）。

## Bug 修复（3）：加载页卡在「正在加载媒体 512 / 943」

**现象**：`AQR10179[18][S]Linear ring Mix…\level.adofai`（981 个媒体，最大一张 14.7MB PNG）打开工作台，加载页停在 512/943 永不关闭。

**根因**：进度按「缩略图内存缓存增长量」算，`MediaThumbnailCacheCapacity = 512`，每次解码都 `TrimMediaThumbnailCache` 削回上限 → `cache.Count - baseline` 永久 512 → `progress` 到不了 1 → 加载页不关。另外 `mediaPreloadPending` 从没被递减过（只赋值一次），`total - pending` 那项恒为 0。**512 这个数字就等于缓存上限**，是铁证。

**修法**（提交 `097cbe0`，`EditorStudioOverlay.cs`）：新增 `mediaPreloadDrained`（出队即 +1）与 `mediaPreloadAlreadyReady = total - queued`；`done = clamp(alreadyReady + drained, 0, total)`；队列空即视为完成（兜底，防永久锁死）；删掉只为旧算法存在的 `mediaPreloadCacheBaseline`。

**没做**：缓存上限仍 512（≈128MB 纹理），不为 943 个媒体拉大；首次解码本身的几十秒成本没改（第二次起走磁盘缓存）。

**通用教训**：**用「缓存增长量」当进度是个陷阱——只要缓存有淘汰上限，进度就会停在那个上限。** 进度应当数「处理了多少个」，不是「缓存里留住了多少个」。

## Bug 修复（4）：68 格后组合运镜幅度比原版大

**现象**：同一张 Linear ring Mix，68 格后连续组合运镜幅度很大。

**根因**：`relativeTo: LastPosition` 的 `rotation` 在原生里是**相对量**。反编译 `ffxCameraPlus.StartEffect`：`num = vfx.camAngle` 只在 `camMovementType == LastPosition` 时赋值，旋转 tween 目标是 `targetRot + num`；其它模式 `num=0`（绝对）。AES 一律按绝对处理 → 每个「LastPosition + rotation 0」把角度瞬移回 0。谱面 68 格后每拍一对 (LastPosition,0 拍,rot 0)+(Player,1 拍,rot 7/20/27/34…)：原版 7→20→27→34 小步上行，AES 每拍 20→0→27→0→34，幅度翻倍且多一记回甩。

**修法**（提交 `5f69e2e`，`CameraPreviewDomain.EvaluateChannels`）：`mode == LastPosition` 时 `target = rotation + keyframe.Rotation`；并补原生那道重启门 `rotationUsed || (movementTypeUsed && movementTypeIsLastPosition)`（没写 rotation 的 LastPosition 也重启，钉在当前角度；NoRotation 钉到 0）。

**注意**：本谱 27 条 LastPosition 里 8 条带非 0 rotation，另有几条完全省略 rotation（8/211/617/1767 格），后者以前根本没被重启。

**工具教训**：`git commit -m` 里带反引号会被 bash 当命令替换，把提交信息吃掉。含代码的提交信息要写成文件再 `git commit -F`。

## Bug 修复（7）：定位点轨道失效（F 引入的回归）

**根因**：F 的走位守卫用了 `NativeRuntimeIsLive(editor)`，它第二项是 `editor.playMode && !editor.inStrictlyEditingMode`。而 `ApplyStaticPreviewState` 会置 `pausedInPlayMode`，**那个字段一置位 `scnEditor.playMode` 的 getter 就无条件返回 true**（项目 7933 行注释已写明"工作台拥有预览的整个期间"）；`inStrictlyEditingMode` 只在 `scnGame.Play` 里被清。→ 预览期间被误判成"原生正在播"，走位开局即被自己取消，点轨道毫无反应。F 之前是直接赋值、没这道守卫，所以是 F 引入的回归。

**修法**（提交 `4b151c6`）：
1. 守卫只认 `previewRequested / previewClockRunning / timelineScrubActive / nativePlaybackStarted / trackBTransportActive`，不再用 `playMode` 计算属性。
2. `EditorSceneInteraction.TryLocateAtPointer` 回退：鼠标抬起、没命中格子、没拖东西时，按世界坐标找最近格（半径 `scrFloor.LongDimensions.magnitude`，与临时碰撞体同 range）直接跳。
3. 四条一次性探针：`[定位] 选格 / 开始走位 / 走位取消 / 回退定位`。

**实测验证**：日志 10 次「选格→开始走位」成对、取消 0 次、回退 0 次、本项目异常 0 条；`求值器自有=True`。

**通用教训**：README/知识库多次提到 `scnEditor.playMode` 是"计算属性、预览期间恒真"，**任何"原生是否在播"的判断都不能用它**，必须用 `nativePlaybackStarted` / `trackBTransportActive` 这类真正由播放入口写入的旗标。

## Bug 修复（11）：自动翻页开关失效（提交 `af35593`）

**根因**：`PageViewAtPlayhead` 判的是 `x > bodyWidth`，但 `QueueScrubAtX` 把拖动位置钳在 `[0, bodyWidth]` —— 播放头**永远越不过右边缘**，那一支在实际拖动里一次都不会成立，功能等于没接上。播放中又是 `FollowPlayback` 在 88% 就跟着挪，也轮不到它。

**修法**：判据改"碰到边缘"（1.5px 容差）；反向加 `currentTime > 0.001` 门（否则 t≈0 每帧空翻）；翻页后 `ClampViewStart` 若夹回原处则直接 return（不置脏不记日志）。加 `[翻页]` 探针（每场景最多 5 行）。

**试过又撤回**：一度把 `FollowPlayback` 也收进这个开关 + 默认改 true，但那会让"默认关闭"的用户播放时时间轴不跟 —— 属于行为回退，已回退，只保留"拖到尽头翻页"这一件事归开关管。

**教训**：**给拖动类交互写"越界"判据前，先确认那边的坐标没有被 clamp**。这次是"条件永远不成立"，表现为"功能完全没反应"，很容易被误判成"按钮没接上"。

### 真实现象补充（提交 `61edb90`）
用户复述："开的时候能翻页，关的时候也能翻页" —— 这才是真缺陷。当时有**三条**自动滚路径，只有 `PageViewAtPlayhead` 受开关约束：
1. `PageViewAtPlayhead`（拖到尽头）✅ 受；
2. `FollowPlayback`（播放中 88% 就挪）❌ 无条件；
3. `SyncCenteredView`（跟随＝固定中间，每帧摆）❌ 无条件。

后两条任意一条在跑，"关掉开关"就看不出区别。改法：三条统一用同一个 `autoPage` 布尔；关 = 完全不自动滚（播放不跟、拖到尽头不翻、居中也不摆）。`AutoPageTimeline` 默认改回 `true`（保持"播放时跟随"这个既有行为，开关只负责"能关掉"）。

**通用教训**：给已有功能加开关时，**先把该功能的所有写入点列全**（这里有三处），否则开关只关掉其中一条，用户看到的就是"开关没用"。

## Bug 修复（12）：拖动后起播，音乐「凭空消失几十上百毫秒」（提交 `e7ac641`）

**根因**：排程要留余量 `MinSchedulingLeadSeconds = 0.1`（否则一半概率晚一个缓冲区 42.7ms），但旧代码把余量**也加到了片段位置上**：`clipTime = rawClipTime + startLead` → 音频晚 0.1 秒开始、却从 0.1 秒之后的内容播 → **那 0.1 秒音乐被剪掉**。画面照常前进，所以音画仍同步，听感是"内容消失 + 顿一下"（与用户描述完全一致）。

**修法**：`clipTime = rawClipTime`；画面在 `[现在, 排程时刻)` 定帧（`holdPictureForAudioStart` + `audioStartDsp` + `MaxAudioStartHoldFrames` 兜底）；**倒计时前奏（rawClipTime<0）不定帧**（那次 startLead 是真实内容长度，可能 2 秒）；回调落地时不再顺手清 `audioStartDsp`。

**实测**：日志 `[AudioStart] 定帧等待 16/8/13 帧后与音乐同时开始`，异常 0 条。

**权衡**：起播时画面停约 0.1 秒（原来是从音乐里剪掉这 0.1 秒）。用户抱怨的是音乐缺失，所以把代价挪到画面。调小 `MinSchedulingLeadSeconds` 能缩短停顿，但缓冲区量化风险会回来（变成音画偏移）。

**追加（`716530c`）**：第一版改完音画脱拍——只改对了片段位置，**锚点 `dspTimeSong` 没跟着后移**，于是 dsp 推导的场景时间比音乐内容快 0.1 秒。修法：定帧那条路锚点改成 `currentDspTime + startLead`。用户确认"可以了"。

## Bug 修复（13）：加载遮罩期间空格会在黑屏底下播歌（提交 `4036af3`）
uGUI 遮罩是 GraphicRaycaster + Backdrop，**只挡鼠标不挡键盘**；空格走到 `EditorUpdateInputPatch.Prefix` 的 `togglePlayback` → 求值器预览开始播歌。修法：`EditorStudioOverlay.IsLoadingScreenShowing`，`Prefix` 在遮罩期间仅在"真有输入那一帧"整帧吞掉（`return !Input.anyKeyDown`），无输入帧照常放行。

## 待验证（14）：定位/翻页快捷键全失效（提交 `84d4adf`）
可疑点是 **Alt**：中文输入法常把 Ctrl+Alt+字母 当全局热键吃掉。改法：`Ctrl+Shift+字母` 也认（两组都要求 Ctrl），并加 `[快捷键]` 探针打印 ctrl/alt/shift 状态、L/P 的 GetKeyDown、`Input.inputString`，用来区分"Unity 没收到"和"被别的判断挡掉"。
**教训**：给功能加快捷键时，Alt 组合在中文输入法环境下不可靠，优先不含 Alt 的组合。
